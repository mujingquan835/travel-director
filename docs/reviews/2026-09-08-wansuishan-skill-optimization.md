## 3. 五项问题的诊断

### 3.1 抽帧为什么接近一小时

实际 `scanner_result.json` 的 270 段计时合计：

| 项目 | 秒 | 解释 |
|---|---:|---|
| 单片 total 累计 | 2759.78 | 约 46 分钟，不含所有启动与问答时间 |
| frame_scan | 2730.02 | 约 45.5 分钟；包含探测、代表帧选择和缩略图阶段，不是纯解码独立计时 |
| 单独记录的 cv | 23.95 | 不能把总耗时归因于这部分质量指标 |
| detector / vision_model | 0 / 0 | 本地视觉模型没有参与 |

源码 `scanner/sampling.py`：探测点数为 `min(24, ceil(duration*2))`，每个点启动一次 FFmpeg，并单独 seek 解码；选出代表帧后又逐张启动 FFmpeg 生成较大缩略图。本次按元数据与配置计算为 3794 个探测调用，加实际 1038 张代表帧对应调用，共约 4832 次进程启动。此为代码和配置推算，不是 OS 进程跟踪实测。

`scanner/pipeline.py::scan_manifest` 使用串行列表推导。运行配置 `hardware_acceleration=none`。禁止外部服务与本地并行无关，过程说明的“本地所以无法并行”解释错误。

另外，14 段未观察素材已有 1–2 张代表帧：8 段为 2 帧、6 段为 1 帧。`agent_batches.py` 要求 3–5 帧才建接触表，导致这些素材进不了观察。可能与短片和视觉去重有关，不应据此宣布源视频不可用。

处理方向：快速档先固定稀疏采样；比较单次顺序解码和少量 seek 的耗时；尽量复用已解码图像；入选候选才做密集采样和运动精查。硬解和并发需在本机小样本比较，不能仅加参数便宣布加速。并发从 1/2 worker 比较，限制子进程线程数，记录内存与温度/负载造成的退化，不能盲目启动几十个任务。

### 3.2 文档而非剪映草稿

45 个槽位没有确定的素材与 in/out。现有 `clip_selector.py` 有独立选片函数，`render.py` 有预览工具，但正式 Runner 本次没有把它们接起来；且现有选片评分以时长、质量、运动、相邻多样性为主，不能直接等同于理解“铁骑沙场”“火树银花”的可靠导演。

导出目录只有 Markdown 路径，未见正式剪映导出实现。不能只修改 SKILL.md 声称支持；需要真实片段计划、音频计划、导出适配器及剪映实机验收。

还有质量冲突：创作方案要求 80–90 秒收束，而实测音乐高潮延续到约 102 秒，交付仍在 80–90 秒高密度快切；90 秒剪断原曲后也没有可验证的收尾设计。音乐长度够用不代表结构符合目标。

### 3.3 90 秒改 60 秒为何重扫

素材事实与剪辑意图被绑定在同一项目冻结状态。`runner.py::_prepare_local_scanner` 只查项目内完整 scanner_result，新项目没有它便重跑整个 scan_manifest。`scanner/cache.py` 虽有 cache_key 和 cache-links，但当前正式扫描路径没有跨项目逐素材命中复用；整批最终结果未完成时，恢复也不能依靠现有单片证据保证跳过已完成工作。

已有 `music_version.py` 可以继承视觉结果换音乐，较新工作树也能同音乐修订时间线。但它们没有直接解决目标时长修改；不能对用户说“已有版本功能所以这个问题已经解决”。

应分离：素材库版本、剪辑需求版本、音乐版本、时间线版本。90→60 只使创作段落、选片排布、声画落点与导出失效，原片事实、缩略图、已确认语义仍有效。换音乐只分析新音频。单个原片变动只更新该片及依赖它的结果。

### 3.4 Token 是否都花在图片上，便宜模型是否够用

日志有 231 条带 usage 的记录，provider messageId 均不同；模型记录为 Kimi-K3 135 条、GLM-5.3 96 条。这不是一次统一模型的成本实验。

| 口径 | 合计 |
|---|---:|
| input_tokens | 35,213,208 |
| 其中 cache_read_input_tokens | 33,406,357 |
| 输入减缓存读取 | 1,806,851 |
| output_tokens | 108,615 |

这些是会话逐记录累计，包含反复输入的历史上下文。缓存约占输入 94.9%。**不能把 3521 万输入当成 3521 万新内容，也不能按未缓存单价换算费用。** output 的推理是否拆分，以原提供方口径为准，不另外重复加总。数据库的 used/size 更不能直接替代累计用量。

按时间切分，扫描结束后至视觉批次完成（16:45:57–17:29:40）为 93 条 usage，输入 11,255,498、缓存读取 10,943,509、输出 48,856，约占全会话输出 45%。区间包含读代码、拼图、写脚本和校验，不是纯图像编码消耗。输入中没有可用的 image_tokens 拆分，无法精确算出图片占比。后续仍有确认、创作、重扫排错、音频与交付文档成本。

27 个观察结果 JSON 共约 1.89 MB，但原会话已经用紧凑标注加脚本补全结果；不能把文件大小当作模型直接输出 token。该优化应正式内置，免去每次临时编写脚本。

建议按职责分工：

| 工作 | 执行方式 |
|---|---|
| 格式、时长、亮度、模糊度、哈希、路径、计时、校验 | 本地确定性代码，无 LLM |
| 建筑/马术/夜秀/人群等粗标签、疑似可用性 | 可替换的低成本视觉模型，短上下文、短 JSON |
| 镜头候选排序、段落结构、风格与声画决策 | 较强模型只读摘要和候选证据 |
| 关键动作入出点、火花爆发、马匹过场、遮挡 | 对入选区间补看时间序列；必要时升级模型 |
| 清单展开、证据链接、草稿字段、媒体复制、导出检查 | 本地代码 |

目前没有“最普通模型已够用”的实测证据。粗筛必须使用具备图像输入能力的模型，文本模型不能直接替代看图。先用本次素材中 30 段做比较：日景、暗夜、火花、马术、人群、1–2 帧短片各 5 段；标注可以弃权，弃权进入复核，不能当成不存在。建议门槛：关键候选召回至少 95%、虚构主体为 0、保留动作区间正确率至少 90%，未达标只升级失败任务类型，不让全量重跑。

基准样本是本轮拟新增的成本/质量评测，不能冒充或重建历史丢失的 blind_annotation。未经实际独立标注和运行，这些均为验收目标。

### 3.5 音效为什么没有落轨

当前交付仅记录相对路径和音量建议。旧 main 的 Hook 选择主要按类别/时长，并随机挑 Hit；新版工作树已改进确定性，但确定性不等于声画匹配。独立 render.py 只混 BGM 和部分原声，并没有把外部 Hook 音效计划直接接入本次交付链路。

音效必须从具体事件出发，形成 `asset + source_in/out + timeline_start + gain + fade + ducking`；选择马蹄、火花、转场风声不能只靠目录名字。先检查并试听原声是否可用，再选择本地音效；允许有意留白，不强制每镜头加效果。找不到真实资源时标缺口，不填假路径。

建议把 BGM、原声、氛围、重点效果分轨，预览与草稿消费同一个音频事件计划。BGM 压低及恢复必须实际写入混音/关键帧，并检查峰值、尾音截断和试听效果。

## 4. 目标架构与变更范围

`素材资产索引 → 稀疏观察 → 紧凑语义 → 音乐适配 → 候选区间精查 → 真实时间线 → 音效落轨 → 剪映草稿 + 预览`

素材资产缓存键以内容身份和提取算法版本为核心，独立于音乐/成片秒数。观测缓存另外包含模型/提示词版本与证据帧身份。mtime/size 可用于快速发现候选变化，但最终使用已核验的内容身份；不可把同名文件视为相同内容。缓存只对发生变化的依赖失效。

剪辑时间线统一采用整数微秒并绑定 FPS；记录每段素材区间、目标区间、速度、画面变换、音频事件和字幕。导出器做映射，不能再次创造镜头决策。

文件划分建议（实施前在功能工作树核对已有实现，避免重建同名职责）：

| 新增 `director/music_edit_plan.py` | 实际使用的音乐区间、拼接、淡出与结构重映射 |

## 6. 新版 Skill 的核心规则

1. 开始先确定本轮是规划还是可编辑草稿；用户说剪辑默认走草稿主交付。
2. 扫描前检查输入规模、运行版本、缓存、编辑器可交付性；轻量确认目的与画幅，已有信息不重复问。
3. 素材扫描与任何音乐/时长选择解耦，不因需求修订启动全量重扫。
4. 普通素材做稀疏观察，候选与不确定素材再精查；不为低价值字段阻塞全片。
5. 代码负责路径、哈希、单位换算、JSON 展开和导出；模型负责证据约束的选择与创意。
6. 音乐的长度合格、结构匹配、听感可接受是三个不同结论。
7. 音效必须有真实资产与落轨记录；缺资源要可见，不用文字规划充当实施。
8. 缓存失效、重试和错误仅影响对应阶段；无进度变化用后台状态，不让模型高频轮询。
9. `plan_ready`、`draft_written`、`draft_verified`、`preview_verified` 分开，只有交付验证满足时才标 `completed`。
10. 每阶段记录用时、调用数、缓存命中、新增解码、视觉输入数、token 口径、失败和重试；`external_call_count=0` 仅表示 Runner 未另调外部服务，不代表会话模型免费或所有图像均本地理解。
