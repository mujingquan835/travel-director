## 2026-08-31 V0.2 产品修正

以下修正优先于本文后续的 V0.1 音乐驱动流程；旧内容保留作为历史背景，不再作为当前第一阶段的开发顺序。

1. 当前主链路改为：`整条素材事实观察 → 用户描述规范化与确认 → 意图条件化素材判断 → 项目级导演方案 → 离线音乐风格推荐`。
2. Scanner 只提供证据，不在扫描或素材理解阶段生成、消费“最佳区间”；`source_in/source_out` 只属于后续音乐时间线阶段。
3. 自动视觉识别是可替换增强层。低置信度、模型不可用或能力门失败时，必须通过本地人工确认完成 assisted 流程，不能填充伪确定事实。
4. 每条素材使用由源文件 SHA-256 派生的稳定 `material_id`；相对路径只用于展示和编辑器重连。
5. 画面事实修订记录在 `visual_confirmation.json`，导演桶位/职责/强制保留或排除记录在独立 `director_review.json`；两者都保留原值、修改值、时间和理由。
6. `director_review.json` 不包含时间区间，避免重新引入已取消的“最佳区间”。
7. 曲多多、即梦、具体曲目搜索、音乐生成、剪辑时间线、音效和编辑器集成都不属于本阶段。
8. 后续时间线形成后，可以通过 OpenTimelineIO 把内部 JSON 映射到 Kdenlive 人工精剪；不得让 `.kdenlive`、LosslessCut 或任何 GUI 工具替代内部证据链和 FFmpeg 自动预览。

V0.2 的完整合同、能力门、开发/盲测拆分和实施顺序以 `docs/superpowers/plans/2026-08-31-visual-understanding-and-director-decision-v2.md` 为准。

## 1. 产品定义

旅行导演面向“已经拍摄了大量旅行素材，但不会选音乐、踩点和组织节奏”的普通用户。

产品不是先完整理解每条视频，再从画面推导故事；第一版的核心是：

1. 快速识别和整理大量素材，排除重复、废片和明显不可用片段。
2. 将素材画像与用户填写的地点、风格、目标时长等需求汇合。
3. 从曲多多网页检索少量可试听的音乐参考方向。
4. 用户选择一个参考方向后，由智能体生成结构化音乐蓝图和即梦 CLI 提示词。
5. 即梦生成相近鼓点、相近风格但不复制具体旋律的原创配乐。
6. 解析生成音乐的呼吸点、上升段、高潮点和收尾落点。
7. 让画面服务于音乐，从候选素材中向时间线槽位填入镜头。
8. 只为真正进入时间线的镜头生成或选择音效，并判断是否保留原始现场声。

一句话定义：**先形成音乐结构，再用经过快速识别的素材填空。**

## 2. 已确认的主流程

```text
导入 100—200 条或更多素材
        │
        ├─ 后台立即进行快速画面识别
        │   去重、排废、场景、运动强度、视觉亮点
        │   原声价值、可选片段、音效候选事件
        │
        └─ 用户同时填写需求
            地点、旅行类型、目标时长、横竖屏
            期望风格、情绪、节奏强弱
                    ↓
汇合“素材画像 + 用户需求”
                    ↓
智能体生成曲多多搜索方案
关键词、流派、情绪、BPM 范围、乐器、时长
                    ↓
浏览器进入曲多多，抓取当前可见的少量搜索结果
                    ↓
向用户展示 3 个音乐参考方向并提供试听入口
                    ↓
用户选择一个方向
                    ↓
智能体把参考方向转换为不含曲名的音乐蓝图
                    ↓
智能体生成即梦 CLI 提示词
                    ↓
即梦生成目标时长的原创音乐
                    ↓
分析生成音乐的节拍与段落
前奏、上升、呼吸、高潮、收尾
                    ↓
按音乐结构创建时间线槽位
                    ↓
从已识别素材中选择、裁切并填入镜头
                    ↓
只对入选镜头生成/选择音效，处理现场声
                    ↓
输出第一版混剪
```

逻辑依赖是“画面识别结果 + 用户需求”共同驱动音乐检索。交互上两项可以并行：素材导入后扫描立即开始，用户在等待期间填写需求。

## 3. 原始素材数量与成片素材数量

原始素材数量不等于最终使用数量。100—200 条素材可能包含大量重复、误拍、废片和相近机位，它们的价值是提供选择余量。

```text
原始素材
  -> 去重、排废、质量筛选
候选素材
  -> 按音乐结构、视觉多样性和镜头强度选择
最终时间线素材
```

最终镜头数量由以下因素决定：

- 目标成片时长，首版支持 30—180 秒。
- 生成音乐的 BPM、段落长度和节拍密度。
- 呼吸段、上升段和高潮段的比例。
- 各段平均镜头停留时长。
- 可用素材的种类、重复度和有效率。

Scanner 不按原始素材总数强制分配时间线位置。

## 4. 画面识别的正确边界

画面识别不是为了完整理解全部素材，而是建立一个可供音乐时间线填空的素材仓库。

### 4.1 全量素材的快速扫描

每条素材第一层只需输出：

- 基础元数据：时长、尺寸、方向、帧率、编解码信息。
- 是否可解码、是否明显不可用。
- 清晰度、曝光和运动强度的原始证据。
- 重复组或高相似组。
- 稀疏代表帧。
- 粗粒度场景和主要视觉对象。
- 视觉冲击力候选。
- 原始现场声是否可能有价值。
- 可能的音效事件标签。
- 推荐保留或二次分析的时间区间。

这一层必须尽可能本地运行、可缓存、可中断恢复，不逐帧调用重型视觉模型。

### 4.2 入选候选的二次分析

只有进入候选池的素材才进一步判断：

- 更准确的可用起止区间。
- 明显运镜和运动方向。
- 最强视觉瞬间。
- 适合低能量、上升、高潮或收尾中的哪一类槽位。
- 是否存在值得保留的动作声、环境声或表演声。

### 4.3 暂停扩张的字段

第一版不继续深挖：

- 固定 A-roll/B-roll 二分类。
- 主角身份识别。
- 游客、演员、同行者之间的精确人物关系。
- `people_present => human_story` 之类的直接推断。
- 对全部素材逐帧生成故事描述。

现有 30 条人物验证集保留，用来防止“画面里人很多就被误判成人物主线”的回归；暂不新增主角标注集。

## 5. 音乐检索原型

### 5.1 输入

音乐检索条件由两个来源共同生成。

素材画像示例：

- 城市、自然、人文、演出、美食、交通等内容分布。
- 日景/夜景比例。
- 高、中、低运动素材比例。
- 有效素材数量和可支撑的成片时长。
- 安静素材、强动作素材和高潮候选是否充足。

用户需求示例：

- 去了哪里、旅行类型。
- 目标时长和发布平台。
- 期望风格、情绪和节奏强弱。
- 是否接受人声、电子鼓、民族乐器等。

### 5.2 智能体生成搜索方案

输出应是结构化条件，而不是一条笼统自然语言：

```json
{
  "keywords": ["旅行", "城市漫游", "明亮", "探索"],
  "genres": ["轻电子", "流行器乐"],
  "moods": ["轻快", "有推进感"],
  "bpm_min": 110,
  "bpm_max": 120,
  "instrument_preferences": ["木吉他", "合成器", "电子鼓"],
  "vocals": "instrumental_preferred",
  "target_duration_seconds": 60
}
```

具体词表与映射在原型验证后再冻结，不在设计阶段假设曲多多页面一定具备全部筛选项。

### 5.3 曲多多网页抓取边界

原型阶段采用浏览器辅助检索，不采用全站爬虫：

- 每个项目只执行一次或少量用户触发的搜索。
- 只读取用户当前浏览器可见页面中的候选信息。
- 默认只返回 3 个方向，内部候选上限 5 条。
- 抓取字段以页面实际可见内容为准：标题、标签、BPM、时长、作者/厂牌、详情页或试听入口。
- 不批量遍历曲库，不绕过登录、验证码、WAF 或访问频率限制。
- 不下载、重新分发或长期缓存受保护的试听音频。
- 遇到登录、验证码或风控时暂停，让用户手动完成，不尝试规避。
- 原型抓取验证的是选曲价值和交互闭环，不代表已经获得商业接入授权。

从第一天使用可替换 Provider：

```text
MusicCatalogProvider
  ├─ QuduoduoBrowserProvider   # 原型网页检索
  └─ HIFIVEApiProvider         # 后续官方 API 接入
```

Director、用户选择界面和音乐蓝图生成不得直接依赖曲多多 DOM 结构。

### 5.4 候选展示

产品面向小白，默认只提供 3 个方向，每个方向包含：

- 一句通俗描述。
- 适合当前素材的理由。
- 可试听入口。
- BPM、情绪、主要乐器和大致节奏。

用户只做一次核心选择，不要求先调十几个音乐参数。

## 6. 音乐蓝图与即梦生成

用户选择参考方向后，智能体提取高层音乐属性，形成不含具体曲名、不要求复制旋律的音乐蓝图。

```json
{
  "duration_seconds": 60,
  "bpm": 116,
  "meter": "4/4",
  "genre": "轻电子旅行器乐",
  "instrumentation": ["木吉他", "轻合成器", "电子鼓"],
  "vocals": "none",
  "sections": [
    {"start": 0, "end": 8, "role": "intro", "energy": 0.25},
    {"start": 8, "end": 24, "role": "rise", "energy": 0.55},
    {"start": 24, "end": 31, "role": "breath", "energy": 0.2},
    {"start": 31, "end": 54, "role": "climax", "energy": 0.9},
    {"start": 54, "end": 60, "role": "outro", "energy": 0.35}
  ],
  "ending": "明确落点，不淡出"
}
```

即梦提示词由该蓝图生成。所谓“生成类似”只指鼓点密度、流派、乐器、情绪和能量结构相近，不复制参考音乐的具体旋律、歌词或编曲细节。

即梦 CLI 当前虽然已经安装，但本阶段尚未验证登录状态、真实音乐命令、独立音效能力、任务耗时、积分消耗和输出格式。开发时必须先做只读能力检查和最小 smoke test，不能根据设想直接编写生产调用。

## 7. 音乐分析与画面填空

即梦生成成功后，以实际音频为准重新分析，不把提示词中的预期时间点当作真实结果。

音乐分析输出：

- 实测 BPM 和拍点。
- 小节与强拍位置。
- 前奏、上升、呼吸、高潮和收尾候选。
- 能量曲线。
- 明确转折或落点。

Director 根据音乐创建时间线槽位：

```text
音乐段落
  -> 本段镜头数量预算
  -> 本段平均镜头时长
  -> 需要的运动强度与视觉类型
  -> 从候选素材中排序选择
  -> 确定具体 in/out 点
```

核心规则：

- 开场优先使用可交代地点和环境的镜头。
- 上升段逐步增加运动、变化和切换频率。
- 呼吸点减少切换、延长镜头并考虑恢复现场声。
- 高潮使用视觉冲击力和运动强度最高的素材，避免提前耗尽强镜头。
- 连续槽位避免相似机位、相似主体和同一重复组。
- 收尾需要明确余韵或落点，不简单耗尽剩余素材。

## 8. 音效与现场声

音效分为“候选识别”和“实际生成/选用”两阶段。

### 8.1 扫描阶段只记录候选

候选事件包括但不限于：

- 海浪、流水、风、雨。
- 脚步、开门、车辆、机械运动。
- 鼓掌、欢呼、演出、游乐设施。
- 食物制作、碰杯、包装和环境细节。
- 甩镜、推进、掠过、快速转向等可使用设计音效的位置。

### 8.2 时间线确定后再处理

只有入选片段才进入 SFX Plan：

- 先检查原始同期声是否比生成音效更真实。
- 确定事件在裁切后时间线中的准确位置。
- 决定使用原声、增强原声、补充生成音效或保持安静。
- 呼吸点优先考虑真实环境声，高潮点才考虑适量强化。
- 不为每个转场都加音效，避免廉价和过度设计。

实际音效生成不与即梦音乐生成同时批量启动，因为多数原始素材不会进入最终时间线。

## 9. 数据对象边界

建议后续实施计划至少定义以下稳定对象：

```text
MaterialScanResult       # 单条素材快速扫描结果
MaterialLibraryProfile  # 项目级素材画像
UserCreativeBrief       # 用户填写的创作需求
MusicSearchBrief        # 结构化曲库搜索条件
MusicCandidate          # 网页抓取的候选元数据与试听入口
MusicBlueprint          # 供即梦生成的原创音乐结构
GeneratedMusicAsset     # 实际生成音乐及调用证据
MusicStructure          # 对实际音频的节拍/段落分析
TimelineSlot            # 音乐驱动的画面槽位
ClipPlacement           # 素材与 in/out 点的时间线放置
SfxCandidate            # 扫描阶段音效候选
SfxPlan                 # 入选镜头的实际音效与现场声计划
```

每个对象必须版本化，失败时显式记录状态，不用默认值伪造成功。

## 10. 失败降级

- Scanner 某字段失败：保留其他字段，不阻断全部素材入库。
- 曲多多页面结构变化：停止抓取并提示用户手动打开搜索结果，不返回伪候选。
- 登录/验证码/WAF：用户手动处理；系统不绕过。
- 无合适参考音乐：允许用户修改方向或手动提供一个参考页面。
- 即梦音乐生成失败：保留音乐蓝图和失败原因，不进入时间线自动剪辑。
- 生成音乐结构与蓝图不一致：以实际音频分析为准重新建立槽位。
- 音效生成失败：优先回退原始现场声或无音效，不阻断视频粗剪。

## 11. 性能与测试停止规则

第一版必须防止再次进入无限测试循环。

### 11.1 性能原则

- 全量素材走快速、稀疏、可缓存路径。
- 重分析只用于候选素材。
- 未进入时间线的素材不生成音效。
- 同一文件内容哈希和分析版本未变化时不重复扫描。
- 先测当前真实素材和当前机器的基线，再设具体时间 SLA；设计阶段不虚构处理速度。

### 11.2 测试轮次上限

每个开发阶段执行：

1. 小样本契约测试和 smoke test。
2. 一次代表性真实素材运行。
3. 一次冻结盲测或端到端验收。

每轮只针对明确的新失败类型修正一次。若没有出现新的失败类型，不重复运行同一整套测试。达到轮次上限后先形成阶段报告，再决定是否扩展实验。

付费调用必须单独记录：调用次数、预计/实际消耗、输出状态和缓存位置。未经用户明确授权，不批量调用即梦或其他付费服务。

## 12. MVP 明确不做

- 不做完整 GUI 和账号系统，除非后续实施计划明确需要最小交互壳。
- 不做全站音乐爬虫或后台持续采集曲多多曲库。
- 不绕过任何登录、验证码、WAF 或付费访问控制。
- 不下载和重新分发曲多多受保护音频。
- 不承诺生成音乐与具体参考曲完全相同。
- 不继续开发 A-roll/B-roll 和主角识别。
- 不对全部素材运行逐帧大模型描述。
- 不在时间线确定前批量生成音效。
- 不把未真实调用的即梦、曲多多或导出链路写成已完成。

## 13. 当前仓库状态

当前 Scanner V0.1 已完成并提交的主要能力：

- 缓存安全的本地扫描管线。
- 本地 SigLIP2、Detector、融合和角色候选实验。
- 字段级评估、静态报告和资源遥测。
- Scanner V0.1 可行性结论。
- 独立 30 条人物验证集及人工标注包。

已确认的问题：旅游场景中“检测到很多人”无法推导 A-roll/B-roll 或人物叙事。该结论用于约束后续 Scanner，不再继续扩张人物语义。

## 14. 新窗口的开发顺序

新窗口不要直接开始网页抓取。先按顺序执行：

1. 阅读本文档和现有 Scanner V0.1 结论文档。
2. 检查当前分支、工作区和现有测试，确认没有接管错误目录。
3. 使用 `superpowers:writing-plans` 编写分阶段实施计划，获得用户复核。
4. 第一阶段先定义上述稳定数据对象和 Provider 接口，不调用外部服务。
